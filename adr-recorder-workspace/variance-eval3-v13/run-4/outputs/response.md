작성하면서 판단한 것들:

- **Status는 Proposed입니다.** `requirements.txt`에 이미 `redis==5.0.8`이 들어가 있지만, 기존 결정 로그를 옮겨 적은 게 아니라 이번에 새로 내린 결정이라 Proposed로 시작했습니다. 실제로 `app/session.py`도 아직 메모리 dict(`_sessions`) 그대로입니다.
- **Alternatives에는 "프로세스 메모리 dict 유지(현행)" 하나만 적었습니다.** 말씀 주신 내용에 나온 대안이 그것뿐이고, 기각 사유(서버 3대로 늘리자 다른 서버로 라우팅될 때 로그인이 풀림)도 분명해서 추가로 여쭙지 않았습니다. 스티키 세션이나 DB 세션처럼 언급되지 않은 선택지는 추측해서 채우지 않았습니다.
- **Review Trigger 섹션은 넣지 않았습니다.** 어떤 조건이 되면 이 결정을 다시 볼지에 대한 얘기가 없었고, 기각 사유를 뒤집어서 조건을 지어내지 않기 위해 생략했습니다. 재검토 기준(예: Redis 운영 부담, 세션 규모 등)이 있으면 알려주시면 추가하겠습니다.
- **Evidence 섹션도 없습니다.** 측정된 수치가 없어서, "서버 3대에서 로그인이 풀린다"는 관찰은 Context에 적었습니다.
- **커밋 인용 주의점 하나:** 최근 커밋 `ba84cb2 feat: 로그인/로그아웃 API`는 `git show --stat`으로 확인해보니 **파일 변경이 없는 빈 커밋**이었습니다. 그래서 메모리 세션 구현의 출처로는 실제로 `app/session.py`를 추가한 `69b2c22`를 인용했고, `ba84cb2`는 롤백 기준점(현재 HEAD 위치 표시)으로만 썼습니다.

Reversibility는 Yes / Migration Cost는 Low로 봤습니다. `get`/`put` 두 함수만 바꾸면 되는 구조라 되돌리는 비용도 낮습니다. 다만 되돌리면 로그인 풀림 문제가 그대로 재현된다는 점을 함께 적어뒀습니다.
