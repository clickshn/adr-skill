# ADR-0002: 세션 저장소를 프로세스 메모리에서 Redis로 이전

- **Status:** Accepted
- **Date:** 2026-09-11
- **Decision:** 로그인 세션 저장소를 프로세스 메모리(`app/session.py`의 `_sessions` dict)에서 Redis로 옮긴다.
- **Scope:** member-portal
- **Decision Source:** Human

## Context

- 현재 세션은 `app/session.py`의 모듈 전역 dict(`_sessions: dict[str, dict]`)에 저장된다. 즉 세션이 각 애플리케이션 프로세스 메모리 안에만 있다.
- 서비스를 서버 3대로 늘리자, 로그인한 서버가 아닌 다른 서버로 요청이 가면 그 서버에는 세션이 없어 로그인이 풀리는 문제가 생겼다.
- 프로세스 메모리 저장 방식은 서버 재시작·재배포 때도 세션이 모두 사라진다.
- 여러 서버가 같은 세션을 볼 수 있는 공유 세션 저장소가 필요하다.

## Decision

- 세션 데이터는 모든 애플리케이션 서버가 함께 쓰는 Redis에 저장한다.
- Python 클라이언트로 `redis==5.0.8`(redis-py)을 `requirements.txt`에 추가했다.
- `app/session.py`의 `get(session_id)` / `put(session_id, data)` 인터페이스는 유지하고 내부 구현만 Redis로 바꾸는 것을 전제로 한다. 그러면 호출하는 쪽(로그인/로그아웃 API)은 고칠 필요가 없다.

## Consequences

**좋아지는 점**
- 요청이 어느 서버로 가든 같은 세션을 읽으므로, 서버를 늘려도 로그인이 풀리지 않는다.
- 애플리케이션 서버를 재시작·재배포해도 세션이 유지된다(Redis가 살아 있는 한).
- 로드밸런서에 sticky session 같은 설정을 걸지 않아도 된다.

**비용·주의점**
- 운영할 인프라 컴포넌트가 하나 늘어난다(Redis 프로비저닝, 모니터링, 백업/장애 대응).
- Redis가 인증 경로의 단일 장애점이 된다. Redis가 장애 나면 로그인 상태 확인이 전부 실패한다.
- 세션 조회 때마다 네트워크 왕복이 생긴다(현재는 메모리 조회).
- 세션 값(`dict`)을 직렬화(예: JSON)해서 저장해야 하므로 직렬화할 수 없는 값은 세션에 넣을 수 없다.
- 지금은 세션이 영원히 남지만(삭제 로직 없음), Redis로 옮기면서 만료(TTL) 정책을 정해야 한다.
- 전환 배포 시점에 프로세스 메모리에 있던 기존 세션은 이전되지 않으므로, 로그인해 있던 사용자는 한 번 다시 로그인해야 한다.

## Alternatives Considered

> 아래 대안과 기각 이유는 ADR 작성 시 초안으로 정리한 것이다. 팀이 실제로 검토한 내용과 다르면 고쳐 주세요.

- **로드밸런서 sticky session:** 앱 수정 없이 가장 빨리 적용할 수 있다. 하지만 서버가 내려가거나 재배포되면 그 서버에 붙은 사용자 세션이 사라지고, 부하가 고르게 분산되지 않는다.
- **RDB(기존 SQLAlchemy 사용 DB)에 세션 테이블:** 새 인프라는 필요 없다. 하지만 요청마다 조회·갱신이 일어나 DB 부하가 늘고, 만료 세션을 따로 정리해야 한다.
- **Stateless 토큰(JWT 등):** 서버에 세션을 저장하지 않는다. 하지만 로그아웃·강제 만료를 구현하려면 결국 차단 목록 저장소가 필요하고, 인증 방식 전체를 바꿔야 한다.

## Open Questions

아래 항목은 결정 시점에 정해지지 않았다. 확정되면 이 ADR에 보충한다.

- 세션 만료(TTL) 시간과 사용할 때마다 연장하는지(sliding expiration) 여부
- Redis 배포 형태(관리형 서비스 / 자체 운영, 단일 노드 / Sentinel·Cluster 등 고가용성 구성)
- Redis 장애 시 동작(로그인 실패 처리 방식, 타임아웃·재시도)
- 영속성(RDB/AOF) 필요 여부. Redis가 재시작되면 세션이 사라져도 괜찮은지
- 접속 정보(URL, 인증, TLS)를 설정으로 주입하는 방식
